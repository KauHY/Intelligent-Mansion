## 3. 人员与图像设计

### 3.1 人员生命周期

1. 新增人员时必须上传人脸照片。
2. 前端校验照片非空，后端也校验照片非空。
3. 后端调用 `/extract` 提取人脸特征。
4. 如果照片中检测到多张人脸，保存失败。
5. 如果照片中检测不到人脸，保存失败。
6. 保存成功后初始状态为待审核。
7. 只有 `status=1` 且 `audit_status=1` 的人员参与识别。
8. 编辑人员照片时重新提取特征。
9. 更换照片不重置审核状态。

### 3.2 图像模型

使用 OpenCV Zoo 的两个模型：

| 模型 | 用途 |
|---|---|
| `face_detection_yunet_2023mar.onnx` | 人脸检测 |
| `face_recognition_sface_2021dec.onnx` | 人脸特征提取与比对 |

### 3.3 特征存储

`mee_face_checkin_person.face_vector` 现在保存 SFace 特征的 `float32 + base64`，不再是原始照片。

`mee_face_checkin_person.photo_path` 仍保存原始照片 base64，用于前端展示和旧数据兼容。

推理服务接口：

| 接口 | 输入 | 输出 |
|---|---|---|
| `/extract` | `photoBase64` | 单人脸照片的人脸数量、图像尺寸、SFace 特征 |
| `/match-feature` | `photoBase64`、`templateFeatureBase64` | 余弦相似度 |
| `/match` | `photoBase64`、`templateBase64` | 旧版照片对照片相似度，兼容旧数据 |

## 4. 相似度阈值设计

当前阈值：

```text
MATCH_THRESHOLD = 0.50
```

调整过程：

1. SFace 官方推荐余弦阈值约为 `0.363`。
2. 该阈值偏向低拒识，但在低质量摄像头下误识风险偏高。
3. 使用本地板端照片样本做了相似度分布检查。
4. 明显同人多帧样本相似度在 `0.70+`，最高约 `0.89`。
5. 综合板端摄像头画质，阈值提升到 `0.50`。
6. `0.50` 能明显降低误识概率，同时不会过度提高拒识率。

后续如果采集更多真实样本，可以继续评估 `0.55~0.60`。阈值越高，误识越少，但低质量画面可能更容易“未识别”。

## 6. 识别与签到逻辑

### 6.1 识别流程

`/verify` 的处理顺序：

1. 校验 `deviceToken`。
2. 按 `deviceId + requestId + meetingReserveId` 做幂等查询。
3. 插入上传请求记录，初始状态未完成。
4. 在 `status=1` 且 `audit_status=1` 的人员中比对。
5. 逐个候选打印人员 ID、姓名、相似度。
6. 取最高相似度人员。
7. 最高相似度低于 `0.50` 时进入未识别流程。
8. 匹配成功后检查是否为当前会议成员。
9. 非会议成员写入“非与会人员”记录。
10. 已签到则返回“已签到”，不重复写入成功签到。
11. 会议时间窗外写入时间窗记录。
12. 会议窗口内且考勤截止时间后签到，标记“迟到”。
13. 成功签到写入考勤记录。
14. 上传请求记录更新为对应结果。

### 6.2 识别分类

| 分类值 | 名称 | 业务含义 |
|---:|---|---|
| 1 | 与会人员 | 人员库中存在，且是当前会议成员 |
| 2 | 非与会人员 | 人员库中存在，但不是当前会议成员 |
| 3 | 非记录人员 | 人员库中不存在或未匹配到已审核人员 |

### 6.3 签到状态

| 状态 | 含义 | 是否进入签到名单 |
|---:|---|---|
| 1 | 签到成功 | 是 |
| 2 | 重复签到 | 可保留事件 |
| 3 | 无权限 / 非与会人员 | 是 |
| 4 | 未识别 / 非记录人员 | 是 |
| 5 | 签到未开始或已结束 | 是 |
| 7 | 处理失败 | 失败时通常事务回滚 |

### 6.4 幂等规则

当前有三层幂等：

1. **请求幂等**：`deviceId + requestId + meetingReserveId` 相同且已完成，返回原始结果，不重复处理。
2. **与会人员幂等**：同一会议中同一人员已有成功签到记录，再次识别返回“已签到”。
3. **非与会人员幂等**：同一会议中同一人员已有同一状态记录，不重复插入。
4. **非记录人员幂等**：同会议内已记录的非记录人员照片与新照片一致时直接返回已记录，不新增记录。

说明：

- 成功签到只保留一条 `status=1` 记录。
- 非成功事件保留最新一次记录，用于审计和分类展示。
- `requestId` 幂等已经加入会议 ID，避免板端重启后同 ID 影响其他会议。

## 7. 板端与 PC 桥接设计

### 7.1 板端上传协议

板端向 PC `9000` 发送：

```text
XPH1 + request_id + width + height + byte_size + crc32 + format
RGB565 raw pixels
```

PC 校验后回 ACK：

```text
XPA1 + request_id + crc32
```

随后 PC 会继续发送识别结果 JSON：

```json
{
  "status": 1,
  "message": "签到成功",
  "personName": "张三",
  "employeeNo": "1001",
  "personType": 1,
  "participantCategory": 1,
  "meetingReserveId": "xxx",
  "meetingSubject": "xxx",
  "requestId": "1",
  "timestamp": "2026-10-22 18:00:00"
}
```

板端侧可以基于该 JSON 做状态显示；当前固件对 JSON 的消费程度需要以后续板端代码为准。回传协议的完整定义、时序与板端消费建议见 §7.4。

### 7.2 图像转换

`api_bridge.py` 的处理：

1. 接收 RGB565 原始帧。
2. 校验 CRC。
3. 回 ACK。
4. RGB565 转 JPEG。
5. JPEG 转 base64。
6. 调用 `/verify`。
7. 解析后端结果。
8. 打印识别日志。
9. 将识别 JSON 回传板端。

### 7.3 日志能力

PC 桥接日志包含：

- 连接时间和对端地址。
- 图片 ID、宽高、字节数。
- 心跳：运行时长、连接数、接收图片数、最近结果、当前会议、回传送达数与回执数。
- 识别结果：会议 ID、会议主题、人员姓名、员工类型、工号、状态、消息、请求 ID。
- 回传结果：`[board-result]` 行输出图片 ID、JSON 字节数、`delivered`（yes/no）与送达模式（`eof`=板端读完关闭，`ack`=板端回执 1 字节；`delivered=no` 表示板端在 JSON 写入前已断开，旧固件预期行为）。

板端串口日志通过 `COM5:115200` 采集，写入：

```text
code/pc_bridge/device_control.log
```

前端会议详情页会读取 `9010 /logs` 展示桥接日志和板端日志。

### 7.4 识别结果回传板端协议（已实现，待板端联调）

PC 在 ACK 之后通过**同一条 TCP 连接**继续下发识别结果 JSON。当前走线为网线（W5500 以太网）直连，联调目标即 `photo_ethernet.h` 这条链路；WiFi（ESP8285 AT）模式见本节末尾的差异提醒。

#### 7.4.1 现状与缺口

| 端 | 现状 |
|---|---|
| PC（`api_bridge.py`） | ✅ 已实现：ACK 后发 `4 字节长度前缀 + JSON`，随后 `shutdown(SHUT_WR)`，3 秒窗口内收板端回执（0 或 1 字节均算送达）；发送失败只记 `[board-result] delivered=no` 日志，不影响识别主流程 |
| 板端（`photo_ethernet.h`） | ✅ 已实现（2026-10-24，主机 gcc 场景测试全绿，待板端联调）：ACK 校验通过后继续读 4B 长度前缀与 JSON 本体（`PHOTO_ETH_JSON_TIMEOUT_MS` 3000ms），解析 `status` 后按预烘焙点阵显示状态文案；完整消费 JSON 才回 1 字节回执；任何 JSON 阶段失败均降级 `photo_status=0`（默认"人像已完成采集"文案），`photo_state` 保持 4 不重采 |

#### 7.4.2 报文格式

第二阶段紧跟 12 字节 ACK（`XPA1 + id + crc`），同一连接：

```text
+---------------+-----------------------------+
| 4 字节         | JSON 长度（网络字节序 u32）   |  ← struct '!I'
+---------------+-----------------------------+
| N 字节         | JSON UTF-8 本体             |  ← 无换行分隔，按长度定界
+---------------+-----------------------------+
```

JSON 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | int | 1 签到成功 / 2 重复签到 / 3 非与会人员 / 4 未识别 / 5 时间窗外 / 7 处理失败（与 §6.3 一致） |
| `message` | string | 后端原始消息（中文） |
| `personName` | string\|null | 识别出的姓名，未识别为 null |
| `employeeNo` | string\|null | 工号 |
| `personType` | int\|null | 1 工作人员 / 2 访客 |
| `participantCategory` | int\|null | 与会类别 |
| `meetingReserveId` | string | 会议 ID |
| `meetingSubject` | string\|null | 会议主题 |
| `requestId` | string | 幂等请求 ID（`{started_at}-{photo_id}`） |
| `boardText` | string | **板端 LCD 直接显示的短文案**：成功类带姓名（如 `张三 签到成功`），失败类只有状态词（如 `未识别`），保证单行点阵放得下 |
| `timestamp` | string | PC 本地时间 `YYYY-MM-DD HH:MM:SS` |

#### 7.4.3 时序

```text
板端                                PC (api_bridge.py)
 │ XPH1 头 + 153600B RGB565  ──────▶ │ 校验 CRC32
 │                                    │ 保存照片、转 JPEG 调 /verify
 │ ◀────── 12B ACK (XPA1+id+crc) ─── │
 │ (当前固件: wiz_sock_close)          │ sendall(4B 长度 + JSON)
 │ (联调固件: 继续读 4B 长度)           │ shutdown(SHUT_WR)  ← JSON 发完标记
 │ ◀────── 4B + JSON (≤1KB) ──────── │
 │ 按长度读完 JSON                     │ 等 3s：板端回 1B 回执或直接关闭
 │ 可回 1B 回执(可选)，然后 close       │ 记 [board-result] delivered=yes mode=eof/ack
 │ photo_state=4 → LCD 显示 boardText  │
```

关键点：

1. **长度前缀定界**：板端先读 4 字节得 JSON 长度，再精确读该长度，不依赖 EOF 或换行。
2. **`shutdown(SHUT_WR)` 是“PC 发完了”的信号**：W5500 收到 FIN 后进入 `SOCK_CLOSE_WAIT`，此时 RX 缓冲里未读的数据**仍然可读**（`socket.c:416-419`：`SOCK_CLOSE_WAIT` 且 `recvsize != 0` 时继续读不报错），所以板端完全可以在 PC 半关闭后继续读完 JSON。
3. **EOF 的表现是负错误码**：RX 读空且连接处于 `SOCK_CLOSE_WAIT` 时，W5500 驱动会自动 close 并返回 `SOCKERR_SOCKSTATUS`（负值）。板端伪代码必须“先判断 JSON 是否收齐、再处理错误码”，不能把 n<0 一律当失败。
4. **回执可选**：板端读完 JSON 后可以直接 close（PC 按 `mode=eof` 记账），也可以回 1 个任意字节（PC 按 `mode=ack` 记账）。回执不是协议要求。
5. **整个第二阶段 ≤3 秒**：PC 回执窗口 3 秒超时后即关闭连接走下一轮检测，板端读慢了 JSON 已送达但收不到回执确认，不影响板端侧显示。

#### 7.4.4 板端消费建议（伪代码，等 bin 编译环境后实现）

> **2026-10-24 已按本节实现**（联调前先以主机 gcc 场景测试验证，见 docs/10 §10）。实现与伪代码的差异：
>
> 1. **JSON 解析不用 cJSON**：`status` 是受控单行 JSON 的首个整数字段，用 ~30 行极简扫描器（`photo_bridge.h` 的 `photo_json_result`）提取即可；cJSON 库在库但 `CONFIG_LIB_USING_CJSON` 未启用，为解析一个字段引入构建依赖不值。
> 2. **LCD 显示按 `status` 选预烘焙位图**，不渲染 `boardText` 全文：6 个状态短语（签到成功/已签到/非与会人员/未识别/未在签到时段/处理失败）由 `pc_bridge/generate_status_fonts.py` 生成 28 行高单色位图（`photo_status_font.h`）；姓名不上板（动态 CJK 字库对板端 flash 不可承受，被拍者即本人，姓名在 PC 日志与 web 端可查）。解析失败或未知 status 回退索引 0（现成"人像已完成采集"）。
> 3. **回执策略更诚实**：仅 JSON 完整消费后才回 1 字节（`pe_receipt`，含 TX 排空等待），降级路径不回——PC 心跳的 `board_ack` 计数只统计"板端真的看懂了结果"，伪代码的无条件回执做不到这一点。
> 4. **EOF 判定按实测驱动语义**：`wiz_sock_recv` 读空且 CLOSE_WAIT 时返回负 `SOCKERR_SOCKSTATUS`，短读一律视为流损坏走降级（伪代码中"EOF 后 break 再判断收齐"的分支在实际驱动语义下等价于负值即降级，因为 JSON 没收齐时降级与 break 后判 received<need 是同一结果）。

原伪代码保留如下作为协议参考：

```c

/* 建议：第二阶段读 JSON，失败不影响 state=4 的成功语义。 */

received = 0;

    if (pe_expired(start, PHOTO_ETH_JSON_TIMEOUT_MS)) goto json_fail;
    int32_t n = wiz_sock_recv(PHOTO_ETH_SOCKET, (uint8_t *)&need + received, 4 - received);
    if (n == SOCK_BUSY) { PrivTaskDelay(1); continue; }
    if (n < 0) break;                       /* 半关闭后读空：EOF，走收齐判断 */
    received += n;
}
need = /* ntohl */;
received = 0;
while (received < need) {                   /* 再读 JSON 本体 */
    if (pe_expired(start, PHOTO_ETH_JSON_TIMEOUT_MS)) goto json_fail;
    int32_t n = wiz_sock_recv(PHOTO_ETH_SOCKET, json + received, need - received);
    if (n == SOCK_BUSY) { PrivTaskDelay(1); continue; }
    if (n < 0) break;                       /* 同上：EOF 不是失败 */
    received += n;
}
if (received == need) {
    photo_json_parse(json);                 /* 提取 boardText/status */
    photo_state = 4;                        /* 与现有时序一致，LCD 显示 */
} else {
json_fail:
    printf("[photo-ethernet] json stage=%s got=%u/%u\n", stage, received, need);
    photo_state = 4;                        /* 降级：仍显示固定"人像已完成采集" */
}
/* 可选：回 1 字节让 PC 心跳的 board_ack 计数生效 */
(void)pe_send((const unsigned char *)"1", 1, PrivGetTickTime());
wiz_sock_close(PHOTO_ETH_SOCKET);
return 0;
```

要点：

- JSON ≤ 1 KB，板端静态缓冲给 `2 KB` 足够；`PHOTO_ETH_JSON_TIMEOUT_MS` 建议 3000（与 PC 回执窗口对齐）。
- **JSON 读取失败必须降级而不是失败**：图片已 ACK、签到已落库，读不到 JSON 只损失 LCD 文案，不能把 `photo_state` 拉回 0 重新采图（那会造成重复签到请求）。
- LCD 渲染建议复用 `photo_toast_font.h` 的点阵管线：优先显示 `boardText`，字体缺失字符回退现成的“人像已完成采集”。`boardText` 里的中文按现有 28×21 点阵规格逐字生成（`pc_bridge/generate_toast_font.py` 可复用）。
- 本节伪代码只覆盖**网线（W5500）链路**；WiFi 模式（ESP8285 AT 解析器 `pw_ack` 仅 12 字节，ACK 后多余字节会触发 `PW_ERROR`）如需同样功能，需先给解析器加 JSON 通路，另行设计。

#### 7.4.5 联调 checklist

板端固件编译环境就绪后按序验证：

1. ☐ PC 侧单测先行：`python -m unittest discover -s pc_bridge -p "test_board_result.py" -v`（已就绪，4 用例：旧固件降级、新固件 EOF、新固件回执、boardText 映射）。
2. ☐ 主机固件场景测试（2026-10-24 已绿，无需板端）：`python pc_bridge/test_ethernet_firmware.py`——真实固件头文件在主机 gcc 下编译，mock W5500 API 覆盖 10 类故障注入 + JSON stage2 解析/回执/legacy 降级 + LCD 渲染计数，再走一次真实 C 二进制帧 → `tcp_bridge` PC 接收器 → PNG → ACK 回环。
3. ☐ 旧固件行为回归：不改编译烧录，跑一次识别，确认 PC 日志出现 `[board-result] delivered=no`（旧固件预期）且识别/签到主流程不受影响。
4. ☐ 新固件烧录后同一会议再识别：PC 日志 `delivered=yes mode=ack`（新固件回 1 字节），板端串口日志出现 JSON 长度与内容打印（`board result json=…`）。
5. ☐ LCD 显示：六种状态短语按 `status` 正确渲染（含姓名的成功场景显示"签到成功"状态词而非全名文案，见 7.4.4 差异 2）；未识别/失败场景显示对应状态词。
6. ☐ 断网/降级：识别后立即拔网线，确认板端走 `json_fail` 降级仍显示默认"人像已完成采集"文案，PC 心跳 `board_json_delivered` 不虚增。
7. ☐ 旧 PC 软件兼容：若 PC 端退回无 JSON 版本（或联调期间误跑旧 `tcp_bridge.py`），确认板端 stage2 读取超时后降级显示，主流程不受影响（主机测试已覆盖 json_mode=0 场景）。

## 15. 当前已知限制

1. Web 端启动的是 PC 接收服务，不是板端远控开关。
2. 板端识别 JSON 消费与 LCD 状态文案固件已实现（docs/10 §10），主机 gcc 场景测试全绿；剩余确认手段是按 §7.4.5 checklist 上板联调。
3. 照片仍以 base64 存数据库，长期应迁移对象存储或文件服务。
4. 推理服务对每个人遍历比对，人员数量增加后性能会下降。
5. 推理服务生成的临时图片没有清理。
6. `9010` 固定 token 仅适合当前联调环境，生产需要改造为受控授权。
7. `/verify` 当前在网关白名单中，生产需要限制来源或增加设备签名。
8. CSV 防公式注入还不完整。
9. 日志中不应长期保留完整人脸 base64，后续需要脱敏和生命周期管理。
