# 11. 人脸采集链路交接文档（板端采集 → 上传 → PC 识别 → 回传 → 板端显示）

> 面向对象：后续接手硬件（edu-riscv64 / K210 / W5500）联调与开发的同学。
> 更新时间：2026-10-24。协议与设计细节的权威出处是《09_人脸识别签到模块进度与详细设计报告.md》§7（板端桥接）与《10_人脸识别签到模块扫描与修复记录.md》§10（本轮固件改动）；本文不重复它们，只讲"拿到手怎么跑、怎么判断好坏、坏了往哪查"。

## 1. 这条链路目前可用吗？（诚实版）

分三层，不要混淆：

| 层 | 状态 | 依据 |
|---|---|---|
| PC 侧全套（tcp_bridge / api_bridge / device_control + 后端 + 前端） | ✅ 可用，已实机跑通 | 2026-10-23 实测日志：板端实拍照片经网线到达 PC，调后端识别返回结果，Web 详情页可见 |
| 板端固件（本轮 H-3 改动：JSON 消费 + LCD 状态文案） | ⚠️ 代码完成、主机测试全绿、**未上板** | `pc_bridge/test_ethernet_firmware.py` 双 PASS（真实固件头文件在主机 gcc 下编译 + 全场景故障注入）；RISC-V 编译环境就绪后按 §5 checklist 联调 |
| 上板后预期行为 | ✅ 设计上向后兼容 | 旧固件（不读 JSON）与新固件都能工作，PC 端不挑固件版本；未联调前的所有"板端显示"结论均以实测为准 |

也就是说：**现在拿一套新硬件，用现有 PC 侧 + 未改固件就能跑通"采集→上传→识别→Web 查看"**；板端 LCD 显示签到结果这一段，要等固件编译环境准备好、烧录 H-3 之后才生效。烧录之前跑起来也不会坏——旧固件 ACK 后直接关连接，PC 会记 `[board-result] delivered=no` 并继续正常工作。

## 2. 链路全景（一图流）

```text
┌─────────────────────── 板端（K210 + XiUOS/XiZi）───────────────────────┐
│ DVP 摄像头 → KPU YOLOv2 人脸检测 → 连续 5 帧有人 → 触发                │
│   photo_state: 0 idle → 1 requested → 2 sending → 4 saved → 0         │
│                                                                       │
│ W5500 TCP（192.168.50.2 → 192.168.50.1:9000）                         │
│   上行：24B XPH1 头 + 153600B RGB565                                   │
│   下行：12B XPA1 ACK → 4B JSON 长度 + JSON → 半关闭                    │
│   （新固件：读 JSON → 回 1 字节回执 → 关连接）                          │
│                                                                       │
│ LCD：底部居中显示状态点阵 2 秒后擦除                                    │
└───────────────────────────────────────────────────────────────────────┘
                    │ TCP 9000（网线直连/同交换机）
                    ▼
┌─────────────────────── PC（pc_bridge/）──────────────────────────────┐
│ api_bridge.py :9000                                                   │
│   1. 收图 → 校验 CRC32 → 先落盘 PNG → 才回 ACK                        │
│   2. PNG → JPEG → base64                                              │
│   3. POST /smartPark/park-meeting/face-checkin/verify                 │
│      （经 gateway :8099 → park-meeting :30011）                       │
│   4. ACK 之后同一连接回传 4B+JSON 结果，3s 窗口等回执                  │
│   5. 心跳/日志：api_bridge.log；串口日志另由 device_control 采集       │
└──────────────────────────────────────────────────────────────────────┘
                    │ HTTP
                    ▼
┌─────────────────────── 后端（docker compose）─────────────────────────┐
│ gateway :8099（verify 在白名单）→ park-meeting :30011                  │
│   token 校验 → requestId 幂等 → 查有效会议 → 调 face-inference :8901   │
│   → YuNet 检测 + SFace 比对（阈值 0.50）→ 分类 → 签到落库 MySQL        │
│ 前端 :9001 会议详情页：启动/停止桥接、看识别结果与签到名单              │
└──────────────────────────────────────────────────────────────────────┘
```

一次识别的实测节奏（2026-10-23 日志）：板端连接后 1 秒内传完图，PC 落盘+识别约 2 秒出结果，整个"人站到镜头前 → 结果可用"约 3~5 秒（含 5 帧确认）。

## 3. 硬件清单与接线（抄作业版）

| 项 | 值 | 备注 |
|---|---|---|
| 板 | edu-riscv64（K210 + XiUOS XiZi_IIoT） | 沿用已调通 YOLO 的那套配置 |
| 摄像头 | 板载 DVP（OV 系列） | 320×240 RGB565，180° 翻转由 `photo_orientation.h` 处理 |
| 网口 | 板载 W5500，SPI1 | 引脚 CLK=9 / D0=11 / D1=10 / SS0=12，RST=13 / INT=14，10 MHz |
| LCD | 板载（320×320） | `LCD_SIZE=320`，toast 画在底部 |
| 串口 | COM5（PC 侧），115200 8N1 | 只用于看日志/收板端日志，**不传照片** |
| 网线 | 直连 PC 有线网卡或经交换机 | 静态 IP，无 DHCP |

网络地址（改板端需重新编译烧录，`photo_ethernet_config.h`）：

| 端 | IP | 掩码 | 网关 |
|---|---|---|---|
| PC 有线网卡 | 192.168.50.1 | 255.255.255.0 | 不需要 |
| 板 | 192.168.50.2 | 255.255.255.0 | 0.0.0.0 |

多块板：每块板改不同的 `PHOTO_ETH_IP` 和 `PHOTO_ETH_MAC`，PC 端不变。

## 4. 怎么跑起来（PC 侧三件套）

前置：Docker compose 全套已起（`docker/docker-compose.yml`，8 容器；关键端口：gateway 8099、park-meeting 30011、前端 9001）。登录账号见 docs/08 §3.3（runlian）。

**方式 A：脚本直启（推荐联调时用）**

```powershell
# 1. 识别桥接（绑定会议 ID；会议 ID 从 Web 端会议列表拿）
.\Start-Ethernet-Checkin.cmd 2112867938806198274

# 2. 设备控制 + 板端串口日志（另一窗口）
.\Start-Device-Control.cmd
```

**方式 B：Web 端操作（演示用）**

前端会议详情页有"启动识别服务"按钮 → 走 nginx `/face-checkin-device/` → `host.docker.internal:9010` → `device_control.py` 拉起 `api_bridge.py` 子进程。注意：`device_control.py` 必须先在 PC 上手动跑着（Start-Device-Control.cmd），Web 只能控制它，不能替你启动它。

**方式 C：只要图像不要签到（老流程，tcp_bridge.py）**

```powershell
python -u pc_bridge/tcp_bridge.py --port 9000   # 只收图存 PNG + ACK，不调后端、不回 JSON
```

这用于固件传输层单独联调；跑它时新固件会走 JSON 读取超时 → 降级显示默认文案，属预期。

启动成功的标志（`api_bridge.log` 或控制台）：

```text
[start] tcp=0.0.0.0:9000 api=http://localhost:30011 device=k210-001 meeting_id=...
[connection] peer=192.168.50.2:xxxxx meeting_id=...
[photo] id=1 size=320x240 bytes=153600
[identify] status=1 message=签到成功 person=张三 ...
```

Web 端会议详情页此时应实时出现识别结果与签到名单。

## 5. 板端固件：编译、烧录、联调 checklist

编译环境（RISC-V 工具链虚拟机）就绪后：

1. 按 `pc_bridge/ETHERNET_SETUP.md` §同步源码、编译与烧录 同步这几个文件到虚拟机代码树（**本轮新增了两个**，别漏）：
   - `photo_bridge.h`、`photo_ethernet.h`、`photo_ethernet_config.h`、`photo_toast_font.h`

2. `make BOARD=edu-riscv64 menuconfig` 保持既有已验证配置（W5500/SPI1/LCD/POSIX 等，清单见 ETHERNET_SETUP.md §48-59），**无需开 cJSON**（本轮固件不依赖它）。
3. `make BOARD=edu-riscv64` → K-Flash 烧录。
4. 联调按 docs/09 §7.4.5 checklist 逐项走，重点：
   - ☐ 启动标志：`[photo] confirm=5 ... rearm=10`、`[photo-ethernet] W5500 TCP enabled`
   - ☐ 触发采图：5 帧确认后上传，串口出现 `board result json=103 {"status":...}`
   - ☐ LCD 显示六种状态文案正确（对照 `tmp/photo_bridge/status_toasts.png` 预览图）
   - ☐ PC 日志 `delivered=yes mode=ack`（新固件回执）而非 `delivered=no`（旧固件）
   - ☐ 拔网线/旧 PC 软件：降级显示"人像已完成采集"，不重复签到

## 6. 协议速查（抓包/调试时对着看）

### 6.1 上行：XPH1 头（24 字节，大端）

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 | `'XPH1'` 魔数 |
| 4 | 4 | photo_id（u32，板端自增，从 1 起） |
| 8 | 2 | 宽 =320 |
| 10 | 2 | 高 =240 |
| 12 | 4 | 数据长度 =153600（320×240×2） |
| 16 | 4 | CRC32（数据部分） |
| 20 | 4 | 格式 =1（RGB565） |

之后紧跟 153600 字节 RGB565 像素。

### 6.2 下行：ACK（12 字节）+ JSON（第二阶段）

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 | `'XPA1'` |
| 4 | 4 | photo_id（回显） |
| 8 | 4 | CRC32（回显） |

ACK 之后**同一连接**继续：4 字节 JSON 长度（大端 u32）+ JSON 本体（UTF-8 ≤1KB），然后 PC `shutdown(SHUT_WR)` 半关闭。板端读完可回 1 字节（任意值，PC 只看有无），也可直接关。

JSON 字段（完整定义见 docs/09 §7.4.2）：

```json
{"status":1,"message":"ok","personName":"张三","employeeNo":"1001",
 "personType":1,"participantCategory":null,"meetingReserveId":"...",
 "meetingSubject":"...","requestId":"1792759621-1",
 "boardText":"张三 签到成功","timestamp":"2026-10-24 14:00:00"}
```

status 语义（与后端签到状态一致，docs/09 §6.3）：

| status | 含义 | 板端 LCD |
|---|---|---|
| 1 | 签到成功 | 签到成功 |
| 2 | 重复签到 | 已签到 |
| 3 | 无权限/非与会人员 | 非与会人员 |
| 4 | 未识别/非记录人员 | 未识别 |
| 5 | 时间窗外 | 未在签到时段 |
| 7 | 处理失败 | 处理失败 |
| 其他/解析失败 | — | 人像已完成采集（默认） |

注意：板端**不渲染 `boardText` 全文**（姓名不上板），只按 status 选预烘焙位图；`boardText` 的价值是给将来升级 LCD 字库时用，以及 PC 日志可读。

### 6.3 超时参数（`photo_ethernet_config.h`）

| 参数 | 值 | 含义 |
|---|---|---|
| `PHOTO_ETH_CONNECT_TIMEOUT_MS` | 10000 | TCP 连接建立上限 |
| `PHOTO_ETH_FRAME_TIMEOUT_MS` | 30000 | 图像发送上限 |
| `PHOTO_ETH_ACK_TIMEOUT_MS` | 10000 | 等保存确认上限 |
| `PHOTO_ETH_JSON_TIMEOUT_MS` | 3000 | 第二阶段 JSON 读取上限（与 PC 回执窗口对齐） |

## 7. 板端代码导读（改哪里前先读这里）

全部在 `XiUOS/App_Framework/Framework/knowing/kpu/k210_yolov2_detect_procedure/`：

| 文件 | 职责 | 改动敏感性 |
|---|---|---|
| `k210_yolov2_detect.c` | 主循环：检测 → `photo_on_detection`/`photo_send_frame` → LCD 刷新 → `photo_show_saved` | 集成点固定在 :464-465/:500，别动 |
| `photo_bridge.h` | 状态机 + 触发/重武装逻辑 + JSON 解析器 + LCD 渲染 | 核心业务逻辑 |
| `photo_ethernet.h` | W5500 会话：网络自检→连接→发图→ACK→**第二阶段读 JSON→回执**→close；`json_fail` 降级路径 | 协议时序核心，改前先看 docs/09 §7.4.3 时序 |
| `photo_ethernet_config.h` | IP/端口/socket 号/超时 | 换网络环境只改这里 |
| `photo_status_font.h` | 7 张状态位图（生成物） | **不要手改**，改 `pc_bridge/generate_status_fonts.py` 的 `phrases` 后重新生成 |
| `photo_toast_font.h` | 默认文案位图（生成物） | 同上（`generate_toast_font.py`） |
| `photo_orientation.h` | 摄像头 180° 翻转 | 装反了改 `PHOTO_CAMERA_ROTATE_180` |
| `photo_wifi.h` | ESP8285 WiFi 链路 | **不含 JSON 通路**（`pw_ack` 仅 12B），本轮未动；要 WiFi 显示需另行设计 |

板端固件改动的安全网：主机测试不需要 RISC-V 环境，改完先跑：

```powershell
python pc_bridge/test_ethernet_firmware.py
```

它会用真实固件头文件在主机 gcc 下编译并注入 10 类故障（超时/断连/错 CRC/JSON 缺斤短两等），任何协议时序改坏都会在这里先暴露。Python 侧测试：`python -m unittest discover -s pc_bridge -p "test_*.py"`。

## 8. PC 侧代码导读

`pc_bridge/` 下与这条链路相关的：

| 文件 | 职责 |
|---|---|
| `api_bridge.py` | **签到主入口**：:9000 收图→落盘→调后端 verify→回传 JSON→3s 等回执；心跳带 `board_json_delivered/board_ack` 计数 |
| `tcp_bridge.py` | 纯图像接收（老流程），提供 `receive_photo/receive_exact` 供测试复用 |
| `device_control.py` | :9010 控制 api_bridge 启停 + 采集板端串口日志（COM5） |
| `ethernet_firmware_test.c` + `test_ethernet_firmware.py` | 固件主机测试（见 §7） |
| `generate_status_fonts.py` / `generate_toast_font.py` | 位图生成（需 Pillow + 微软雅黑，仅开发机） |

已知设计边界（不是 bug，改需求才改）：
- 照片以 base64 存 MySQL（docs/09 §15 已知限制 3），量大后迁对象存储。
- 推理对全员遍历比对，人数多了会慢（限制 4）。
- `9010` token、`/verify` 白名单是联调态配置，生产要收紧（限制 6/7）。

## 9. 故障排查速查表

| 症状 | 先查 | 依据 |
|---|---|---|
| 板端串口打 `cable link DOWN` | 网线、PC 网卡是否 UP、对端端口 | photo_ethernet.h 会打印 PHY 寄存器 |
| `invalid W5500 version` | SPI 接线/供电/复位 | 版本寄存器读到非 0x04 |
| 连接超时（`connect deadline`） | PC 是否起了 9000 监听、Windows 防火墙入站 | `netstat -ano | findstr 9000` |
| 板端连上但 PC 无日志 | 双方 IP/掩码、`PHOTO_ETH_PC` 是否填的有线网卡地址 | §3 地址表 |
| PC 收到图但 `[error] stage=api` | compose 起没起、`--api-base` 端口对不对（30011 直连或 8099 过网关） | api_bridge.log |
| `status=3 无权限` 但人明明在名单里 | 人员 `audit_status` 是否已审核通过、是否在该会议名单内 | docs/09 §6：只在 status=1 且已审核的人员中比对 |
| `status=5` | 会议时间/考勤时间窗口配置 | 会议编辑页 |
| 板端显示的文案不对 | 抓串口 `board result json=` 行核对 status；确认烧的是新固件 | §6.2 status 表 |
| LCD 无任何 toast | state 是否到 4（串口看 `PC saved`）、`BSP_USING_LCD` 是否开 | photo_bridge.h 守卫 |
| 新固件跑着像旧固件（`delivered=no`） | 烧录的 bin 是否为最新编译产物 | PC 端无法区分固件版本，靠日志行为区分 |
| 识别很慢 | 人员库大小（遍历比对）、首次推理模型加载 | docs/09 §15 限制 4 |
