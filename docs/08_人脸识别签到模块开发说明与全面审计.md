# 人脸识别签到模块开发说明与全面审计

> 更新时间：2026-10-22  
> 适用范围：`code/pc_bridge`、`code/face_match`、`code/smart-park-backend/park-meeting`、`code/face-checkin`、`code/docker`  
> 文档目的：说明当前人脸签到模块怎么用、各组件如何协作、数据如何流转，并记录本轮全面检查发现的代码、业务与逻辑问题。

---

## 1. 结论速览

当前模块的端到端链路已经可以跑通：

```text
K210/XiUOS + 摄像头 + W5500
      | TCP 9000, XPH1 + RGB565 图像
      v
pc_bridge/api_bridge.py
      | POST /smartPark/park-meeting/face-checkin/verify
      v
park-gateway 8099 -> park-meeting 30011
      | 人脸比对
      v
face-inference 8901, YuNet + SFace
      |
      v
MySQL smart-park
      |
      v
前端会议详情页：识别状态 / 上传记录 / 签到名单 / 桥接日志 / 板端串口日志
```

当前可以确认：

- `face-inference` 服务健康检查通过，`/health` 返回 `{"status":"ok"}`。
- 模型使用 OpenCV Zoo 提供的 **YuNet 人脸检测** 与 **SFace 人脸特征识别**。
- 已有人员模板成功参与比对，历史上存在 `SUCCESS` 签到记录。
- `api_bridge.py` 是正式闭环链路；`tcp_bridge.py` 是只负责保存图片的调试工具，不会触发后端签到。
- 板端 LCD 当前只显示“图片已保存”这类 toast，还没有真正消费 PC 回传的识别结果 JSON。
- 2026-10-22 最近两次板端上传请求为 `NOT_RECOGNIZED`，说明“板端 -> PC -> 后端”传输链路通，但当时的识别比对没有命中已审核人员，应继续从图片质量、模板质量和阈值角度排查。

## 3. 日常使用流程

### 3.1 启动服务

如果是首次启动或镜像有变更：

```powershell
cd code/docker
docker compose up --build -d
```

如果服务已经在跑，只做状态检查：

```powershell
cd code/docker
docker compose ps
```

不需要每次都重新构建。只有修改了前端、后端或 `face_match` 代码后，才需要重新 build 对应服务并 recreate。

### 3.2 启动本机设备控制服务

推荐使用：

```powershell
cd code
.\Start-Device-Control.cmd
```

该脚本会：

1. 启动 `pc_bridge/device_control.py`，监听 `9010`。
2. 打开板端串口 `COM5:115200`。
3. 把板端串口日志写入 `code/pc_bridge/device_control.log`。
4. 提供 Web 端“启动识别/停止识别/查看日志”的控制接口。

注意：`Start-Device-Control.cmd` 本身不会启动 9000 桥接进程。9000 由 Web 详情页点“启动识别”时按会议启动。

### 3.3 登录 Web 端

访问：

```text
http://localhost:9001
```

当前测试账号：

```text
runlian / Wf53abc1@
```

登录后进入左侧菜单中的“会议管理”或“人脸识别签到”。

### 3.4 登记人员

在“人脸识别签到 -> 人员管理”中新增人员。

必填信息：

- 姓名。
- 员工类型：内部员工/工作人员或访客。
- 现场人脸照片。

流程要求：

1. 新增人员后默认 `audit_status=0`，待审核。
2. 必须在列表中点击“通过”。
3. 只有 `status=1` 且 `audit_status=1` 的人员会参与识别。

原因：后端 `matchPerson()` 只查询审核通过人员。

### 3.5 创建会议

在“人脸识别签到”页面新增会议时，至少配置：

| 字段 | 说明 |
|---|---|
| 会议主题 | 显示在会议列表和详情页 |
| 会议开始时间 | 会议持续时间的起点，也是识别窗口起点 |
| 会议持续时间 | 用于计算会议结束时间 |
| 考勤开始时间 | 当前用于考勤口径配置 |
| 考勤结束时间 | 超过该时间签到会标记“迟到” |
| 与会人员 | 从已登记人员中选择 |

保存后后端会同时写入：

- `mee_meeting_reserve`
- `mee_face_checkin_member`

会议主题、会议时间、考勤时间、参会人员都会保存到会议预约记录。

### 3.6 在会议详情页启动识别

进入会议详情页后：

1. 确认会议时间尚未结束。
2. 确认 `9010` 状态正常。
3. 点击“启动识别”。
4. 观察识别服务状态、桥接日志和板端日志。
5. 让人员在 K210 摄像头前保持正脸。

Web 端的“启动识别”启动的是 PC 上的 9000 桥接进程，并把它绑定到当前会议 ID。它不是直接向板端发送“开始识别”指令。板端固件会自行持续检测人脸；连续检测到人脸达到阈值帧数后主动向 PC 上传图片。

### 3.7 查看识别结果

会议详情页会展示：

- 最新上传记录和最新识别结果。
- 签到名单：签到时间、人员姓名、工号、员工类型、状态、备注。
- 上传记录：请求 ID、设备 ID、会议 ID、处理结果。
- PC 桥接日志。
- 板端串口日志。

状态含义：

| 状态 | 后端含义 | 前端展示 |
|---|---|---|
| 1 | 签到成功 | 绿色“签到成功” |
| 2 | 重复签到/已签到 | 重复签到事件 |
| 3 | 已识别出人，但不是会议成员 | “无权限” |
| 4 | 没有匹配到审核通过人员 | “未识别” |
| 5 | 当前不在识别时间窗口 | “未开始/已结束” |
| 7 | 后端或依赖处理异常 | “处理失败” |

### 3.8 停止识别

推荐在会议详情页点击“停止识别”。

也可以查询状态：

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:9010/status -Headers @{'X-Device-Control-Token'='local-device-control-token'}
```

停止后 `api_bridge.py` 进程会退出，9000 不再接收板端连接。

## 4. 板端与 PC 桥接说明

### 4.1 板端网络配置

`photo_ethernet_config.h` 当前配置为：

```c
#define PHOTO_ETH_IP       {192, 168, 50, 2}
#define PHOTO_ETH_NETMASK  {255, 255, 255, 0}
#define PHOTO_ETH_GATEWAY  {0, 0, 0, 0}
#define PHOTO_ETH_PC       {192, 168, 50, 1}
#define PHOTO_ETH_PORT 9000
```

即 PC 有线网卡需要配置为 `192.168.50.1/24`，板端为 `192.168.50.2/24`。

### 4.2 图片协议

板端发送格式：

```text
XPH1 + request_id + width + height + byte_size + crc32 + format
RGB565 raw pixels
```

PC 校验 CRC 后回包：

```text
XPA1 + request_id + crc32
```

板端收到 ACK 后关闭 socket，LCD 显示“已保存”提示。

当前板端只等待 12 字节 ACK，不等待、不解析 PC 后续返回的识别结果 JSON。因此“PC 识别成功”与“板端 LCD 显示识别成功”目前不是同一件事。

### 4.3 两个桥接程序的区别

| 程序 | 用途 | 是否触发签到 | 是否保存本地照片 |
|---|---|---:|---:|
| `api_bridge.py` | 正式闭环，接收图片后调用 `/verify` | 是 | 否 |
| `tcp_bridge.py` | 调试工具，只接收并保存 PNG | 否 | 是，保存到 `code/tmp_photos` |

正式运行时不要同时启动两者，否则会争抢 9000 端口。

### 4.4 图片去向

当前链路下：

1. K210 原始 RGB565 帧进入 `api_bridge.py`。
2. `api_bridge.py` 在内存中转成 JPEG，再转 base64。
3. base64 直接放进 `/verify` 的 `photoBase64` 字段。
4. 后端把它保存到：
   - `mee_face_checkin_request.photo_path`
   - `mee_face_checkin_attendance.photo_path`
5. 人员登记时，Web 上传照片 base64 保存到：
   - `mee_face_checkin_person.photo_path`
   - `mee_face_checkin_person.face_vector`

因此当前 `photo_path` 和 `face_vector` 的字段语义已经不符合名称，它们实际上保存的是照片 base64，不是文件路径或特征向量。

推理服务读取照片的方式是：

1. 接收 Java 传来的两张 base64 图像。
2. 写入容器内临时文件。
3. 用 OpenCV 读取。
4. YuNet 检测每张图最大人脸。
5. SFace 提取特征。
6. 计算余弦相似度。
7. 与 `0.363` 阈值比较。

推理服务并不读取 `code/tmp_photos`。`tcp_bridge.py` 保存到该目录只是为了排查板端成像。

## 5. 后端业务规则

### 5.1 核心代码

主实现文件：

```text
code/smart-park-backend/park-meeting/src/main/java/com/crlink/smartpark/meeting/service/impl/FaceCheckinServiceImpl.java
```

`verify()` 的处理顺序：

1. 校验 `deviceToken`。
2. 按 `deviceId + requestId` 幂等查重。
3. 插入 `mee_face_checkin_request`，状态 `0`。
4. 在所有 `status=1` 且 `audit_status=1` 的人员中比对。
5. 未匹配则写入 `NOT_RECOGNIZED`。
6. 匹配后检查是否是当前会议成员。
7. 非成员写入 `NO_PERMISSION`，同时写入无权限考勤事件。
8. 已成功签到则写入 `ALREADY_CHECKED_IN`，同时写入重复事件。
9. 检查会议时间窗口。
10. 通过后写入成功考勤。
11. 根据 `attendanceEndTime` 判断是否标记“迟到”。
12. 更新请求为已完成。

### 5.2 时间规则

当前实现：

```text
识别窗口 = meetingTimeStart ~ meetingTimeEnd
迟到判断 = checkinTime > attendanceEndTime
```

也就是说：

- 只有会议持续时间内才能签到。
- 考勤结束时间不直接阻断识别；在会议结束前识别仍会成功，但会被标记“迟到”。
- `attendanceEndTime` 为空时，回退使用 `meetingTimeEnd`。
- 当前没有使用 `attendanceStartTime` 阻断识别。如果配置的考勤开始时间晚于会议开始时间，会议开始后、考勤开始前扫脸仍然可以成功签到。

这个行为需要产品口径确认。如果希望“考勤开始前不能签到”，需要把识别窗口改为 `attendanceStartTime ~ attendanceEndTime`，或在会议时间内额外校验考勤开始时间。

### 5.3 幂等规则

数据库唯一键：

```sql
UNIQUE KEY uk_device_request (device_id, request_id)
```

后端在插入前先按 `device_id + request_id` 查询。

风险：板端 `photo_id` 会从 1 开始递增。如果 K210 重启后设备 ID 仍是 `k210-001`，请求 ID 会再次从 1 开始，可能命中历史请求，导致新照片被旧识别结果覆盖。建议板端请求 ID 加入启动时间戳、随机数或递增持久化序号。

## 9. 模型与识别口径

### 9.1 模型

使用两个 ONNX 模型：

| 名称 | 文件 | 用途 |
|---|---|---|
| YuNet | `face_detection_yunet_2023mar.onnx` | 人脸检测 |
| SFace | `face_recognition_sface_2021dec.onnx` | 人脸特征提取与比对 |

关键参数：

```text
识别阈值：0.363
人脸检测阈值：0.6
比对方式：余弦相似度
板端图像：320 x 240 RGB565
```

### 9.2 比对逻辑

后端遍历所有审核通过人员，把当前板端照片分别与人员模板比对，取相似度最高者。只有最高相似度大于等于 `0.363` 才认为识别成功。

### 9.3 当前识别失败的可能原因

最近两次板端请求为 `NOT_RECOGNIZED` 时，应优先排查：

1. 板端图片是否过暗、过曝、模糊或角度过大。
2. 人员登记模板是否是高分辨率证件照，与低分辨率 K210 图像差异过大。
3. RGB565 转 JPEG 后颜色/方向是否正确。
4. YuNet 是否在低分辨率图像上检测到人脸。
5. 阈值 `0.363` 是否适合该模板与该摄像头组合。
6. 是否误用了待审核人员。
7. 是否同名但模板不是当前人员本人。

推理服务健康不代表一定识别成功；健康只说明进程活着。

| 推理服务 | `docker logs face-checkin-inference` | 默认抑制 HTTP access log |

| 调试照片 | `code/tmp_photos` | 仅 `tcp_bridge.py` 会写入 |

### 10.2 推荐排查顺序

1. 看板端日志是否有 `detect_info.obj_number`。
   - 一直为 0：没检测到人脸。
   - 变成 1：板端检测到人脸，等待连续帧触发。
2. 看 9010 日志是否有 `connection` / `photo`。
   - 没有连接：板端没触发上传、网络不通或 9000 未监听。
3. 看是否有 CRC/timeout。
   - 有：传输协议或网络稳定性问题。
4. 看是否出现 `[identify]`。
   - 有：桥接已调用后端并拿到结果。
5. 看 `[identify]` 的状态和 message。
   - `NOT_RECOGNIZED`：比对未命中。
   - `NO_PERMISSION`：人已识别，但不是会议成员。
   - `OUT_OF_TIME_WINDOW`：会议时间外。
   - `SUCCESS`：数据库应出现签到记录。
6. 看数据库请求表和考勤表。
7. 如果怀疑图片质量，临时改用 `tcp_bridge.py` 保存 PNG，再人工比对。

### 10.3 常见故障

| 现象 | 常见原因 | 处理 |
|---|---|---|
| Web 点启动无反应 | 9010 没启动 | 运行 `Start-Device-Control.cmd` |
| Web 显示无法连接设备控制 | 9010 未监听或 nginx 代理失败 | 确认 `Start-Device-Control.cmd` 窗口存在 |
| COM5 PermissionError | COM5 被 kflash 或其他串口工具占用 | 关闭占用程序后重启设备控制 |
| 9000 Address already in use | 手工桥接与 9010 启动桥接同时存在 | 只保留一种启动方式 |
| 板端连接失败 | PC IP 不是 `192.168.50.1` 或防火墙拦截 | 检查 IP 和 TCP 9000 入站规则 |
| 有上传但 `NOT_RECOGNIZED` | 图片质量/模板不匹配/阈值不合适 | 用 `tcp_bridge.py` 保存图片并人工比对 |
| 有识别但无权限 | 人员不是会议成员或未审核 | 审核人员并加入会议 |
| 会议时间外 | 当前时间不在会议持续时间 | 修改会议时间或使用测试会议 |
| 详情页打不开 | 路由 ID 或路由名不对 | 使用列表页“详情”按钮进入 |
| 页面不能滚动 | 样式高度固定 | 已修复 `.park-flow` 滚动，如复现检查布局容器 |
| Nacos 不健康 | 内存不足或 Docker 资源不足 | 查看 `docker logs face-checkin-nacos` |

## 11. 本轮代码与业务审计

### 11.1 高优先级问题

| 编号 | 问题 | 影响 | 建议 |
|---|---|---|---|
| H-01 | 板端不消费识别结果 JSON。`photo_ethernet_transfer()` 收到 12 字节 ACK 后立即关闭 socket。`api_bridge.py` 后面发送的 JSON 不会被固件读取。 | 板端只能显示“已保存”，不能显示姓名、工号、员工类型、会议号或签到状态。 | 扩展协议：ACK 后板端继续读取结果 JSON；固件解析后在 LCD 绘制结果；PC 端在发送 JSON 前不要提前关闭。 |
| H-02 | 板端重启后 `request_id` 可能重新从 1 递增，与数据库唯一键冲突。 | 新请求可能被判定为旧请求，直接返回历史结果，导致看起来“扫脸无反应/没签到”。 | 请求 ID 改为 `设备启动时间戳-随机数-递增ID`，或后端允许同一设备重启会话。 |
| H-03 | `photo_path`、`face_vector` 实际保存大段 base64。 | `mediumtext` 记录膨胀，列表接口变慢，数据库备份变大，隐私面扩大。 | 照片存对象存储或受控文件目录，数据库只存 URL/Key；`face_vector` 改存真实 SFace 特征向量。 |
| H-04 | `matchPerson()` 对每个审核通过人员逐个调用推理服务。 | N 名人员就是 N 次 HTTP + N 次人脸检测/特征提取，人多时识别明显变慢。 | 登记时预计算特征向量；识别时只计算一次现场特征，然后在内存/向量库中比对。 |
| H-05 | 推理服务临时文件只创建不删除。 | 容器内磁盘持续增长，人脸临时文件泄漏。 | `_decode()` 返回路径并注册 finally 删除，或用上下文管理器清理。 |
| H-06 | `/verify` 在网关白名单中，设备 token 硬编码为统一值。 | 接口可能被外部调用，token 泄漏后可伪造签到。 | 网关限制来源/内网访问；每设备独立凭据；绑定设备与会议；增加 nonce/签名/时间戳。 |
| H-07 | `device_control.py` 的本地控制 token 写死并暴露在前端代码中。 | 能访问前端资源的人可以看到 token，进而控制本机桥接进程。 | 本地控制服务只绑定 `127.0.0.1`，或通过用户会话换发短时 token；不要把固定 token 打包进前端。 |
| H-08 | 会议软删除后 `listMeetings()` 未显式过滤 `deleted`。实体也没有 `@TableLogic`。 | 删除的会议可能仍出现在列表；识别时 `getById()` 也可能拿到软删除会议。 | 查询统一加 `deleted=0`；`verify/checkTimeWindow` 校验会议存在且未删除。 |
| H-09 | 人员删除是物理/主键删除，但历史签到只保存 `person_id` 和姓名快照，工号/类型查询依赖人员表。 | 人员删除后历史考勤中的工号、员工类型可能丢失。 | 人员改为软删除；或考勤表冗余工号、员工类型、模板版本。 |

### 11.2 中优先级问题

| 编号 | 问题 | 影响 | 建议 |
|---|---|---|---|
| M-01 | 考勤时间窗口合法性校验不足。 | 前端可能校验，但后端没有强制 `attendanceStartTime <= attendanceEndTime` 且两者应位于会议时间内，异常数据会导致迟到判断不可控。 | 后端 `saveMeeting/updateMeeting` 增加统一校验。 |
| M-02 | `verify()` 捕获所有异常后返回 FAILED。 | 异常被 catch 后 Spring 事务不会自动回滚，可能留下状态 0 请求或部分数据。 | 明确哪些异常需要回滚；必要时手动标记 rollback，或将外部调用移出事务。 |
| M-03 | 推理服务不可用时，所有相似度为 -1，最终返回 `NOT_RECOGNIZED`。 | 运维会把依赖故障误判为识别不匹配。 | 区分 `INFERENCE_UNAVAILABLE` 与 `NOT_RECOGNIZED`，并返回更明确错误。 |
| M-04 | `/verify` 与 `/match` 没有请求体大小限制。 | 大 base64 会占用内存和数据库。 | Gateway、Java、Python 三层限制大小；限制图像尺寸与格式。 |
| M-05 | 没有上传频率限制。 | 同一设备可高频刷请求，推理服务单线程会被打满。 | 按 `device_id/meeting` 限流，增加最小请求间隔。 |
| M-06 | CSV 导出做了逗号/引号转义，但没有防公式注入。 | 姓名/备注含 `=`、`+`、`-`、`@` 时，在 Excel 中可能被执行。 | 对以公式前缀开头的单元格加 `'` 前缀或空格。 |
| M-07 | 前端轮询 5 秒，不是实时推送。 | 识别后最多延迟 5 秒，日志也批量刷新。 | 使用 SSE/WebSocket 推送识别结果和日志。 |
| M-08 | `listMembers()`、`listAttendance()` 存在按人员逐条查询的 N+1。 | 成员和签到记录多时接口变慢。 | 用 JOIN 或批量 `selectBatchIds` 一次取人员信息。 |
| M-09 | `saveMembers()` 不校验人员 ID 是否存在、是否审核通过、是否重复。 | 可写入无效成员；页面看不到但数据库有脏数据。 | 保存前批量校验人员存在、未删除、审核通过，并对 personId 去重。 |
| M-10 | 删除会议只软删会议，不清理成员和正在运行的识别绑定。 | 旧 9000 进程可能仍绑定已删除会议；后续请求落入无权限或时间窗外。 | 删除会议时停止对应桥接，或至少提示用户；识别前校验会议有效。 |
| M-11 | `attendance/list` 当前按 `checkin_time DESC` 排序。 | 如果业务要求“从早到晚的签到名单”，当前顺序相反。 | 前端排序或后端按需求改为 `ASC`。 |
| M-12 | `face-inference` 使用单线程 `HTTPServer`。 | 多次识别并发时排队。 | 改为 ThreadingHTTPServer 或异步队列。 |
| M-13 | `device_control.py` 启动子进程时 `stdout=open(...)` 未显式关闭。 | 频繁启动/停止可能留下文件句柄。 | stop 后关闭日志句柄，或统一由日志队列写入。 |

### 11.3 低优先级/工程问题

| 编号 | 问题 | 建议 |
|---|---|---|
| L-01 | 前端本地代理 `config/proxyTable.js` 指向外部测试地址，与 Docker 配置不同。 | 明确本地开发模式说明，避免误连远端。 |
| L-02 | 板端串口日志可能出现非 UTF-8 字节，浏览器显示乱码。 | 固件统一 UTF-8 输出；串口读取按可配置编码/二进制安全处理。 |
| L-03 | `photo_control` 相关历史脚本较多，容易误启动。 | 保留 `api_bridge.py`、`tcp_bridge.py`、`device_control.py`，把历史测试脚本归档。 |
| L-04 | `face_match` 里存在为兼容中文路径复制模型的临时目录逻辑。 | 长期可保证容器内路径为 ASCII；Windows 本地开发再保留兜底。 |
| L-05 | 多个公共配置默认值较弱，例如 MySQL root 密码、Redis 无密码。 | 生产部署改为环境变量或 Secret 管理。 |
| L-06 | 前端代码中包含固定设备控制 token。 | 见 H-07，尽快改为后端代理或会话授权。 |
| L-07 | `MeetingReserve.deleted` 是 Boolean，但业务列表未统一过滤。 | 统一封装查询条件或接入 MyBatis-Plus 逻辑删除。 |

## 14. 当前已知边界

2. 板端 LCD 不显示识别结果，只显示保存 toast。
